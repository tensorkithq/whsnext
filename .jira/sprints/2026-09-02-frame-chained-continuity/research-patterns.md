# Research: patterns — 2026-09-02-frame-chained-continuity

## Summary

- **Q1 (stale guard):** Recommend **(b)** — exempt `{:last_frame, url}` from the beat guard with a dedicated `handle_info` head that stores unconditionally-latest. Option (a) is backwards under the existing guard (it drops the common on-time case and accepts only the late straddle); option (c) is structurally too late (scene_boundary fires 10s AFTER the lock that builds the next ctx) and breaks the "pipeline produces, server consumes" split. The reference impl treats the last frame as latest-ground-truth (run-token guard), while per-beat artifacts stay beat-guarded — exactly split (b).
- **Q2 (delayed close):** A `{:timeline, :vote_close}` scheduled at lock + `reveal_ms` (new key in the `timings` map) is a straight application of the house idiom. Guard shape `%{vote: %{locked: true}}` + fall-through drops any stale close; the below-quorum branch should keep its immediate `vote_closed` — no `vote_locked` precedes it, so there is nothing to reveal, and its cleanup (`vote: nil`) already conflicts with a delayed close.
- **Q3 (reference discipline):** `Whn.Frames` already uses the reference repo's exact recipe (`-sseof -0.25`); the client reference extracts at `duration - 0.05`. Both fall inside the user's "last second of that frame." Keep `-0.25` — it is the spike-proven margin (2,946ms round trip) and safer than −0.05 against end-of-stream misses. FINAL FRAME HYGIENE is already ported into the Celeris system prompt.
- **Q4 (feature hygiene):** Recommend supersession: the new sprint's `features/` dir owns the corrected predicate under a new `@req` id; add one comment line to the old EP-08 scenario pointing forward, leaving its tags and Then-clause intact. In-place rewrite would attribute post-sprint behavior to `@plan:IV` and falsify the PASS verification's 33/33 claim map.

## Findings

### Q1 — Stale-guard evolution for the scene-end frame message

**The house pattern.** Pipeline messages are beat-tagged by the producing cycle (`server/lib/whn/pipeline.ex:140-143` — `notify` always uses `ctx.beat`) and the server drops non-current beats via head match: `server/lib/whn/episode_server.ex:118-122` (`%{beat: beat}` match + silent drop clause). The split is documented on both sides: "the destination applies its own stale-beat guard" (`pipeline.ex:9`), "Messages for any beat other than the current one are stale and dropped" (`episode_server.ex:7-9`). Beat bumps inside `lock_and_start_cycle` (`episode_server.ex:210`), and the next cycle's ctx — including `last_frame_url` — is built in the same handle_info (`episode_server.ex:214`, `pipeline_ctx/2` at `:411-421`). `state.last_frame_url` is written only at init (`episode_server.ex:69`).

**Timing (D-14 defaults, CONTEXT.md:31 + fal-spike.log).** Cycle N is dispatched at the beat N−1 lock. With spike wall-clocks (bridge/i2v ~5s, frame ~2.9s: `fal-spike.log:5,7`), segment 2 lands ~30s after dispatch and its extraction ~3s later — normally BEFORE the next lock (which is 40s after dispatch: 20s of remaining scene N−1 playback + 10s bridge + wait... conservatively, the extraction usually lands mid-scene-N playback, before scene N's lock), but one retry (`pipeline.ex:147-158`, up to 2×16s per stage, `pipeline.ex:24`) pushes it past the lock. Both sides of the straddle occur.

**Option (a) — tag with the beat it feeds (beat+1).** Under the existing guard this is inverted: the on-time arrival (state.beat still N) is DROPPED because the tag says N+1, and only the too-late arrival (after the lock already built ctx without the frame) passes. It also breaks the uniform tag semantics — every other message is tagged with the producing cycle's beat (`pipeline.ex:140-143`), and `Whn.Pipeline` currently has no concept of "the beat I feed." (a) only works if the guard is special-cased anyway, at which point it is (b) with misleading tags.

**Option (b) — exempt `{:last_frame, _}`, store unconditionally-latest.** One new `handle_info` head ordered before the beat-guard pair (clause-specificity ordering is already the house style — `episode_server.ex:116-122`, and every `handle_timeline` guarded head has a fall-through: `:168`, `:182`, `:193`). The brief's pinned shape `{:pipeline, beat, {:last_frame, url}}` keeps the tag for logging even though the handler ignores it. Reference precedent is strong: `tmp/interdimensional-game/lib/engine.ts:97` holds `lastFrame` as a single latest-value field, stored after a run-token check only (`engine.ts:235-238,250`), while the per-beat adjudicator verdict gets BOTH token and beat checks (`engine.ts:311`) — frames are "latest ground truth" (`engine.ts:285`: "The previous frame is still the ground truth"), per-beat artifacts are staleness-guarded. Serial cycles make latest-wins safe in practice: one dispatch per lock, at most one `{:last_frame, _}` per cycle, emitted last. Residual pitfall (bounded): a zombie cycle whose `segment_ready`s were dropped as stale can still complete its trailing extraction and overwrite a fresher frame — worst case one bridge seeds from a one-beat-old frame; the beat tag permits a cheap monotonic check if the planner wants it.

**Option (c) — server extracts at `:scene_boundary` via Task.** Structurally too late AND a layering break. Too late: lock is at scene start +20s, `:scene_boundary` at +30s (`episode_server.ex:26-32`; `advance/1` schedules the boundary at `segments × segment_ms`, `:301`), so the frame would always miss the ctx built at lock (`:214`) and the brief's "bridge generates during remaining scene playback" overlap dies. Layering: the server today never touches `Whn.Fal`/`Whn.Frames`; `episode_server_test.exs` runs on `PipelineStub` alone (`test/whn/episode_server_test.exs:16-18`) with zero ffmpeg/FalMock fixtures, while `pipeline_test.exs:22-41` owns the ffmpeg fixture + FalMock setup. (c) would drag that setup into the server suite and the Task's async result would need a new message shape — re-inventing the pipeline message with a worse home.

**Test shape for (b)** stays inside `server/AGENTS.md:71-78` rules: `send(pid, {:pipeline, 0, {:last_frame, url}})` + `:sys.get_state` sync, then assert the next `{:start_cycle, ctx}` recorded by `Whn.PipelineStub.calls()` carries `ctx.last_frame_url` — same shape as the existing dispatch assertions (`episode_server_test.exs:63-68`). Pipeline side: `pipeline_test.exs:92-110` (pinned-order test) extends by one expected message; extraction naturally sits after delivery because `notify(:segment_ready, 2, url)` precedes `next_frame` in `run_segments` (`pipeline.ex:106-109`), and the change point is the `next_frame(2, _)` skip (`pipeline.ex:126-127`). The opening cycle shares `run_segments` (`pipeline.ex:69`), so the opening scene's end frame seeds beat 1's bridge for free.

**Recommendation: (b).**

**Pitfall — parked ctx staleness (local near-miss shape):** `pending_cycle` stores the ctx snapshot built at lock (`episode_server.ex:221`) and dispatches it verbatim on the presence recheck (`:137-140`). A frame arriving during the hold updates `state.last_frame_url` but not the parked ctx. Planner should refresh `last_frame_url` at dispatch (or rebuild ctx) — one-line fix, easy to miss.

### Q2 — Delayed `vote_closed` via the timeline idiom

**Fit confirmed.** All transitions are `{:timeline, event}` self-messages via `schedule/2` (`episode_server.ex:445`, moduledoc `:3-5`); durations live in the merged `timings` map (`:26-32` defaults, `:50` merge, test-injectable via start attrs, the same mechanism tests already use for `viewer_count_fn` (`episode_server_test.exs:24-32`; no test overrides `timings` yet)). A `reveal_ms` key (~2_500) + `schedule(:vote_close, state.timings.reveal_ms)` replacing the immediate `broadcast("vote_closed", %{})` at `episode_server.ex:204` is the same move D-14 prescribes ("transitions are explicit `{:timeline, event}` self-messages… so tests drive them manually", CONTEXT.md:31). Client needs no change: `vote_locked` sets locked state (`web/src/lib/useEpisode.ts:53`), winner styling keys off `vote.locked` (`web/src/components/vote-overlay.tsx:47,73`), and `vote_closed` tears down (`useEpisode.ts:66`) — verifier finding #2 (`.jira/sprints/2026-08-31-live-episode-mvp/VERIFICATION.md:150`) already diagnosed the back-to-back broadcast as the only problem.

**Guard shape.** House precedent is guarded head + silent fall-through: `handle_timeline(:vote_lock, %{vote: %{locked: false}})` / catch-all (`episode_server.ex:170,182`); `:revote` matches `%{vote: nil, next_choices: [_|_]}` / catch-all (`:184,193`). The matching shape here: `handle_timeline(:vote_close, %{vote: %{locked: true}} = state)` + fall-through. This is sufficient for the revote race: a `:vote_close` can only be scheduled from the quorum-met lock branch (the below-quorum branch never emits `vote_locked` and never would schedule a close), and any subsequently reopened vote has `locked: false` (`episode_server.ex:151-160`), so a stale close falls through instead of tearing down a live poll. In production timings the race is unreachable (next `vote_open` is ≥ bridge + 10s away, `episode_server.ex:302`), but manual-message tests can and should drive it directly. Detail for the planner: after lock, `state.vote` currently lingers locked until the next `vote_open` (join-sync already hides it — `sync_vote` returns nil for locked, `:328`); having `:vote_close` also set `vote: nil` mirrors the below-quorum cleanup (`:178`) and makes a duplicate `:vote_close` fall through on the nil match.

**Below-quorum branch stays immediate.** `episode_server.ex:174-179` broadcasts `vote_closed` with NO preceding `vote_locked` — the client never enters the reveal state, so a delay would just freeze an expired poll with nothing highlighted for 2.5s. The branch also nils the vote and stashes `next_choices` synchronously for `:revote` (`:178`); delaying its close would force keeping dead vote state alive. Keep it immediate; the reveal delay applies only inside `lock_and_start_cycle`.

**Recommendation: `reveal_ms` in `timings`, `schedule(:vote_close, ...)` at lock, guarded head `%{vote: %{locked: true}}` + fall-through, below-quorum branch untouched.**

### Q3 — Reference-impl END-frame discipline

- **Extraction point.** Client reference seeks `video.duration - 0.05` and grabs full-res JPEG at 0.92 quality (`tmp/interdimensional-game/lib/frames.ts:77,83`). The ffmpeg experiment that `Whn.Frames` was built from uses `-sseof -0.25` (`tmp/interdimensional-game/experiments/grab-frames.mjs:10`), byte-identical to production (`server/lib/whn/frames.ex:46`) and D-06 (CONTEXT.md:23). Both offsets sit inside the user's "the last second in that frame"; −0.25 is the safer server-side margin (`-sseof` input-seeks from the nearest keyframe; a −0.05 seek can land past the final decodable frame and emit nothing) and is the recipe the timed spike proved (`fal-spike.log:7` — `STAGE last_frame 2946ms`, the brief's ~3s figure). Nothing to port here — confirm and keep.
- **Storage discipline.** Reference stores exactly one latest frame per run and resets it on new-run boundaries (`engine.ts:97,196,250`); it feeds both the next generation (`engine.ts:426,476,549` — `fromFrame`) and the freeze/hold frame (`engine.ts:261`). Supports Q1's latest-value field over a per-beat collection.
- **Prompt-side hygiene already ported.** The reference's FINAL FRAME HYGIENE rule (`tmp/interdimensional-game/lib/adjudicator.ts:40` — end shots readable, no extreme close-ups/blur, because the last frame seeds the next shot) exists verbatim-in-spirit in `server/lib/whn/prompts.ex:24`. Frame chaining makes this rule load-bearing for the first time in production (it currently guards only within-scene chaining); no new work, but worth a pointer in the plan.
- **Failure discipline.** Reference: a failed shot falls back with "The previous frame is still the ground truth" (`engine.ts:283-288`). Local analog: if the trailing extraction fails, the cycle should NOT report a fatal `{:error, :frame, _}` that flips the episode to hold (`episode_server.ex:265-268`) — the scene already delivered; the next bridge just degrades to the existing `last_frame_url: nil` → t2v path (`pipeline.ex:86-96`). The current `report/3` treats any `{:error, ...}` outcome uniformly (`pipeline.ex:134-138`); the planner should keep the trailing extraction's failure non-fatal.

### Q4 — Feature-file hygiene for the stale EP-08 predicate

**The discipline as practiced.** Each sprint's `features/` dir is sprint-owned: file header `@sprint:<slug>` (`.jira/sprints/2026-08-31-live-episode-mvp/features/episode-core.feature:1`), scenarios tagged `@req:<ID> @plan:<N> @wave:<N>` (`:46` for EP-08). Verification enforces a 1:1 claim map — every `@req` → claiming plan → sensed evidence (`VERIFICATION.md:101-139`; EP-08 row at `:126`), and the PASS verdict counts "33/33 predicates claimed and sensed" (`:143`).

**Evolution precedents so far.**
- *Mid-sprint, pre-verification:* edit in place, recorded as a `plan(...)` commit — `dbfc988` rewrote CEL-01/CEL-02 Given-clauses when D-05 was revised, keeping `@req`/`@plan` tags. Legitimate because the owning sprint's plans were revised in the same commit.
- *Post-sprint:* the quorum-guard commit `ba56bb2` changed EP-08's behavior (below-quorum lock now closes the poll and schedules `:revote` instead of holding — `episode_server.ex:174-179`) and re-annotated the TEST (`episode_server_test.exs:187` — "EP-08 (quorum guard subsumes the old zero-presence hold at lock)") but did not touch the feature file. That is the gap the brief's item 3 names; there is no post-sprint supersession precedent yet — this sprint sets it.

**Why not edit the old scenario's predicate.** EP-08's Then-clause ("the pipeline impl is not invoked and the episode holds", `episode-core.feature:50`) is what 04-PLAN claimed and what verification sensed at `verified_at: 2026-08-31T20:08` (`VERIFICATION.md:3,126`). Rewriting it under the existing `@plan:IV @wave:2` tags attributes behavior to a plan that never specified it and silently desynchronizes the frozen PASS record from the file it audited. The mid-sprint precedent (`dbfc988`) doesn't extend: there, the owning sprint's own plan changed in the same commit.

**Recommendation:** the new sprint's `features/` dir owns the corrected predicate — a scenario under a new `@req` id (fresh id, not a reused EP-08; e.g. the reveal-delay and frame-chain scenarios this sprint needs anyway plus one quorum scenario) tagged `@sprint:2026-09-02-frame-chained-continuity` with this sprint's `@plan`/`@wave`, whose Then-clause states the current truth: below `min_voters` the poll closes without a winner, the same options re-offer via `:revote`, and no generation starts (matching `episode_server_test.exs:96-113,187-202`). In the OLD file, add a single comment line above EP-08 (`# superseded 2026-09-02 by @req:<new-id> (quorum guard, commit ba56bb2) — predicate preserved for the 2026-08-31 claim map`) and leave tags + Given/When/Then untouched. Old claim map stays truthful; a reader of the old file can't act on the stale predicate; the new behavior is attributed to the sprint that owns it.
